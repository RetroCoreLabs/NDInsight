SINTRAN boot and segments: how the operating system gets from a disk pack into memory

A guide for people new to the machine. It follows the load button to the @ prompt, shows what sits where on a pack and in memory, and explains the one thing that trips everyone: the three copies of the resident data page and why a CPU number change has to reach two files.

1

The machine in one picture

An ND-100 (and its faster siblings ND-110 and ND-120) is a 16-bit minicomputer. A program sees 64 K words; physical memory is up to 16 M words in banks of 64 K words. Between the two sits the memory management system: 16 page tables of 64 entries each, every entry mapping one 1024-word page. SINTRAN III gives each table a job and switches tables as it moves between the user, the monitor, the file system and the drivers. Disks are divided into 1024-word pages too, and every disk carries an NDFS directory of named files.

2

Eight words you need

segment

A numbered block of up to 64 KW of code or data that SINTRAN swaps as a unit. It has a logical base inside the 64 KW space, a length in pages, a disk page in a segment file, and a page table it runs in. Names like S3FS are given by the RT-loader.

page table (PIT)

One of the 16 tables of the memory management system. SINTRAN uses each for a role: 7 DPIT for the resident data, 10 RPIT for resident code, 12 MPIT for the monitor and drivers, 4 FPIT for the file system, 11 SPIT for the command processor and loaders, 1 and 2 for the user.

segment file

One contiguous NDFS file holding segments page after page. File 0 is SEGFIL0:DATA. "File 4" is the kernel's name for an absolute save area at disk page 1, which is inside SINTRAN:DATA and MACM-AREA:DATA. Files 1-3 exist only if the installer made them.

segment table

8 words per segment: links, LOGAD (base page), SEGLE (length), MADR (page in its file), FLAG (file number in bits 13-15), status, core-map head. Lives in memory, and on disk as segments 27 (image) and 24 (save) inside SEGFIL0.

DPIT, the resident data page

The data every part of the kernel shares: RT descriptions, device datafields, system variables, the CPU number (SYSNO), the segment-file tables. Logical 4000B in page table 7. Stored as segments 23 (memory), 44 (image on disk), 53 (save on disk).

save / image / running

Most system segments exist three times. The save copy is what the installer wrote; a cold start copies it over the image copy and loads it. The image copy is the working copy; a warm start loads it as it is. The running segment is the one in memory.

symbol list

(SYSTEM)SYMBOL-1-LIST:SYMB and SYMBOL-2-LIST:SYMB: every kernel symbol of that build with its octal address (SYSNO=004051). Every system pack carries its own. Addresses move between builds, so tools read these, never a table.

RTFIL and the name records

The RT-loader keeps every segment name as a "DEFINED SEGMENT NAME" record (type 25B, the name packed as SIXBIT, the segment number) in RTFIL:DATA and in segment 10 S3RTFIL. That is where S3SDPIT = 53 comes from.

3

What is on a system pack

Measured on real K and L packs verified: the kernel lives in three NDFS files at fixed disk pages, and inside SEGFIL0:DATA the generation job laid the system segments out page by page. The bar is the start of SEGFIL0 on an L pack, drawn to scale (one unit = 8 pages, octal page numbers from the listing).

The order and sizes come from section 29.6 of the generation listing (MSSLE / MISLE macros), and the measured segment table of the L packs has the save data page at 100B = page 64 and the image at 1773B = page 1019, exactly as listed. On K the save copies of the data page, system segment and error program are in SINTRAN:DATA instead.

4

The boot, stage by stage

1

Firmware loads one page verified

Pressing LOAD (RetroCore: boot bd0; nd100x: --boot=smd0) runs the ND-100's mass-storage load: the firmware reads disk page 0, 1024 words, into memory at address 0 and starts the CPU at address 0. That is everything the hardware knows how to do.

The CPU trace of the K pack starts at address 0 with PIOF, the first word of that program. ND-06.014.2A §4.2.5.2.
2

The page-0 program loads the kernel source

Those 1024 words are the loader RELOA plus a disk driver. It reads segment 2 S3IMAGE, page 0 of SEGFIL0:DATA, 77B pages of "common / start / restart code", into memory, then jumps to SINTR. SINTRAN itself rewrites page 0 with the current loader at every start, so the bootstrap on a pack is always its own kernel's.

PH-P2-OPPSTART.NPL 3712-3766 (RELOA), 850-876 (the cells it fills and the rewrite). Its untouched copy is segment 52 S3SAVE at disk page 1; on the K pack the two are byte-identical.
3

SINTR sets the system up, paging off source

Entry at SINTR. It turns interrupts off, probes the CPU (SYSEVAL: NORD-10 / ND-100 / ND-110 / ND-120, floating point, instruction set), on an ND-110/120 reads the identity PROM (GCPUNR) and if the signature 52652B is there overwrites SYSNO, FCPUN and the CPU type in memory, scans memory, reads the resident data page from disk into bank 1 at 4000B, builds the page tables, finds the devices, sets up buffers and interrupt vectors. On a cold start it first copies every save segment over its image segment.

Data page from the save copy S3SDPIT when HENTFLAG=0, from the image copy S3IDPIT otherwise (lines 262, 283-284); the 32 save-to-image copies at 771-841; GCPUNR only when SYSEVAL found an ND-110 or later (313).
SINTRAN K stops here on a programmed PROM. verified The K start-up code reads PROM bytes 6-7 and jumps to IOF; WAIT at address 2 when they read 52652B. Nothing is printed. RetroCore and nd100x present no signature until an identity key is set, so K and L packs both boot.
4

Paging on, interrupts on, the monitor runs source

SETPTABL loads or checks the ND-110/ND-120 control store from the micro code segment, maps the resident segments into their page tables and sets the page-table register on every level. Interrupts come on, the monitor starts on level 3 and the idle program on level 1. From now on the data page in memory is the live segment 23 S3DPIT.

5

Initial commands, banner, mode files verified

The start program runs the commands stored in the kernel buffer INIBU: ENTER-DIRECTORY of the system disk first, where the file system compares the directory's page-0 stamp with SYSNO and refuses with 3203 DIRECTORY ENTERED BY ANOTHER SYSTEM if they differ; then SET-AVAILABLE and the mode files. The banner (SINTRAN III - VSX/500 K, CPU TYPE, CPU NUMBER) is printed from the data page. XMSG, the network servers and COSMOS start, and the @ prompt appears.

5

Memory after boot: the page tables and what runs in them

Every table carries the small common code (pages 0-12B) so the kernel's shared routines are reachable whatever table is active, and every system code path uses DPIT (table 7) as its alternative table for data. From the K, M and N release information source.

PIT 1 UPITN user, normal

  • the background or RT program's own segments
  • on disk, "UPITN" in the generation marks copies that are not mapped at run time

PIT 2 UPITA user, alternate

  • the program's second table (data, or a 128 KW program)
  • XMSG kernel and XROUT run here (L and later)

PIT 3 FUPIT remote file user

  • common code
  • page 13: remote file access segment 22

PIT 4 FPIT file system

  • common code
  • page 13: the file system, segment 6 S3FS

PIT 5 5PIT ND-500

  • common code
  • 13: MON 60, segment 51
  • 20: ND-500 system monitor, segment 30

PIT 6 XPIT XMSG

  • common code
  • 13: XMSG (K layout)

PIT 7 DPIT the data table

  • 2: resident common data, 37 K: RT descriptions, datafields, SYSNO, segment-file tables (segment 23)
  • 57: windows to background, ND-500, levels 10/12, 1/4
  • 62: system segment window, 72: data segment
  • 101: device name table (L and later)

PIT 10 RPIT resident code

  • common code, 13: extended common (64)
  • 15: monitor calls, B-level (level 4): segment 47
  • generation 500 and later: segment administration

PIT 11 SPIT SINTRAN programs

  • 13: edit routines (42), always
  • 14: one of: command processor (3), RT-loader (4), DMAC (7), error program (14), service/mail (71), TADADM (36), servers (105-127)

PIT 12 MPIT monitor

  • common code, 13: extended common
  • 15: monitor level, level 14, drivers for levels 10-13, MPERF: segment 35

PIT 13 / 14 X5DP1, X5DP2 ND-500

  • ND-500 name tables (21) and standard domains (20)
  • last page: ND-500 monitor stack window

PIT 15 IPIT I/O (L and later)

  • common code, 13: extended common
  • 15: level 3 and the mass-storage level 11: segment 67

PIT 17 DTPIT direct tasks

  • direct tasks
  • maps DPIT during start-up

Not in any table

  • segment table, memory map
  • RT register blocks and bitmaps
  • big terminal datafields, ND-500 mailboxes, logical device tables
6

The three copies of the data page, and who writes which

Why both disk copies: a cold start copies S3SDPIT over S3IDPIT and loads it, a warm start loads S3IDPIT as it is. A value in only one of them survives only one kind of start. ND's own install run patches S3SDPIT and then demands a cold start; the tool writes both so either start sees it.

7

Finding any segment from the pack alone, with no fixed numbers

Three things on every system pack are enough to find any kernel word on disk, whatever the SINTRAN generation: the symbol lists give the address, the RT-loader name records give the segment number, the segment table gives the page and the file. Nothing is hard-coded, because the numbers move between builds (FCPUN is 105034B on the K pack and 004414B on the L packs).

8

Looking at a pack yourself

Always work on a copy of a disk image. ndtool (repository norskdata-ndfs, folder ndfs-c) reads and changes all of the above from the pack's own files:

ndtool -i -v disk.IMG              directory label, extended info (system number, entered flag)
ndtool -t disk.IMG                 the files: SEGFIL0:DATA, SINTRAN:DATA, RTFIL:DATA, SYMBOL-1/2-LIST ...
ndtool --segments disk.IMG         every segment: number, name, page table, range, length, disk page, file
ndtool --export-segment 53 disk.IMG out.bin      copy one segment out (for carving or comparing)
ndtool --cpu-identity disk.IMG     SYSNO / FCPUN / CPU type / patch level in both copies, 33CPN, the stamp
ndtool -n --set-cpu 21238:9883 disk.IMG          preview a CPU number and type change
ndtool --set-cpu 21238:9883 disk.IMG             write both copies, 33CPN/33CPU, clear the stamp, read back
ndtool --release disk.IMG          clear only the "entered by system N" stamp

In RetroCore, cpu config --cpu=ND120CX boots a K or L pack unchanged; Config cpu_number N makes the emulated PROM override what the pack says, as a real programmed ND-120 would under SINTRAN L. DMAC on a running system does the same patch as --set-cpu, segment by segment.
